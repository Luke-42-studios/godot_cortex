# Systems

> **S** in CELS — Game logic as plain functions organized into domains

---

## Overview

**Systems** are plain functions that query entities and operate on components. They're organized into **domain modules** — self-contained units that handle one aspect of gameplay (movement, combat, AI).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           DOMAIN MODULE PATTERN                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Each domain is a self-contained module:                                   │
│                                                                             │
│   namespace Movement {                                                      │
│       namespace Phase { ... }   // Sub-phases (if ordering needed)          │
│       static void sys(...);     // Systems (private to file)                │
│       void init(Runtime* rt);   // Single entry point                       │
│   }                                                                         │
│                                                                             │
│   Main initialization is clean:                                             │
│                                                                             │
│   void register_game_systems(Runtime* rt) {                                 │
│       Input::init(rt);                                                      │
│       Movement::init(rt);                                                   │
│       Combat::init(rt);                                                     │
│       AI::init(rt);                                                         │
│       Animation::init(rt);                                                  │
│   }                                                                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

> **See:** [examples/domains/game_init.cpp](examples/domains/game_init.cpp) for complete initialization

## Domain Structure

A domain module contains everything needed for one gameplay feature:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                             DOMAIN ANATOMY                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │ namespace Movement {                                                │   │
│   │                                                                     │   │
│   │   // 1. SUB-PHASES (optional - only if ordering matters)            │   │
│   │   namespace Phase {                                                 │   │
│   │       flecs::entity Input;    // Calculate intent                   │   │
│   │       flecs::entity Apply;    // Apply forces                       │   │
│   │       flecs::entity Resolve;  // Read results                       │   │
│   │   }                                                                 │   │
│   │                                                                     │   │
│   │   // 2. SYSTEMS (static = private to file)                          │   │
│   │   static void player_movement(...) { ... }                          │   │
│   │   static void apply_gravity(...) { ... }                            │   │
│   │   static void apply_velocity(...) { ... }                           │   │
│   │                                                                     │   │
│   │   // 3. SINGLE ENTRY POINT                                          │   │
│   │   void init(Runtime* rt) {                                          │   │
│   │       // Create sub-phases                                          │   │
│   │       // Register systems                                           │   │
│   │   }                                                                 │   │
│   │                                                                     │   │
│   │ }                                                                   │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

---

## When to Use Sub-Phases

| Scenario | Sub-Phases? | Why |
|----------|-------------|-----|
| Movement: input → gravity → apply → resolve | **Yes** | Clear data flow, order matters |
| AI: sense → decide → act | **Yes** | Each step needs previous results |
| Combat: damage → death | **No** | Simple, order within file is fine |
| Animation: play animations | **No** | No ordering dependencies |

## Example: Movement Domain (With Sub-Phases)

Movement needs precise ordering — calculate intent before applying forces.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         MOVEMENT EXECUTION FLOW                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Phase_Physics                                                             │
│       │                                                                     │
│       ├── Movement.Input ─────────────────────────────────────────────────  │
│       │   └── PlayerMovement: Read input, calculate velocity direction     │
│       │                                                                     │
│       ├── Movement.Apply ─────────────────────────────────────────────────  │
│       │   ├── ApplyGravity: Add gravity to velocity.y                      │
│       │   └── ApplyVelocity: Call move_and_slide()                         │
│       │                                                                     │
│       └── Movement.Resolve ───────────────────────────────────────────────  │
│           ├── ResolveVelocity: Read back collision-adjusted velocity       │
│           └── CheckGrounded: Update Tag::Grounded                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Key Pattern: Sub-Phase Creation

```cpp
void init(Runtime* rt) {
    flecs::world& w = rt->world();
    flecs::entity physics = rt->get_phase(Phase_Physics).id;

    // Create sub-phases with explicit dependencies
    Phase::Input = w.entity("Movement.Input")
        .add(flecs::Phase)
        .depends_on(physics);

    Phase::Apply = w.entity("Movement.Apply")
        .add(flecs::Phase)
        .depends_on(Phase::Input);   // Runs after Input

    Phase::Resolve = w.entity("Movement.Resolve")
        .add(flecs::Phase)
        .depends_on(Phase::Apply);   // Runs after Apply
}
```

## Example: Combat Domain (Simple)

Combat doesn't need sub-phases — systems run in registration order.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          COMBAT EXECUTION FLOW                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Phase_Physics                                                             │
│       │                                                                     │
│       ├── ApplyDamage: Process pending damage                               │
│       ├── CheckDeath: Add Tag::Dead if health <= 0                          │
│       └── HealthRegen: Regenerate health over time                          │
│                                                                             │
│   No sub-phases — order by registration within init()                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Key Pattern: Direct Phase Registration

```cpp
static void apply_damage(Health& hp, DamageQueue& dmg) {
    // Process pending damage
}

static void check_death(flecs::entity e, Health& hp) {
    if (hp.current <= 0) e.add<Tag::Dead>();
}

void init(Runtime* rt) {
    flecs::world& w = rt->world();
    flecs::entity physics = rt->get_phase(Phase_Physics).id;

    // Systems run in this exact order (registration order)
    w.system<Health, DamageQueue>("ApplyDamage")
        .kind(physics)
        .each(apply_damage);

    w.system<Health>("CheckDeath")
        .kind(physics)
        .without<Tag::Dead>()
        .each(check_death);
}
```

## Cross-Domain Dependencies

When one domain needs results from another, add explicit dependencies.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        CROSS-DOMAIN ORDERING                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Movement must complete before AI senses positions:                        │
│                                                                             │
│   Movement.Input ──> Movement.Apply ──> Movement.Resolve                    │
│                                                │                            │
│                                                v                            │
│                                         AI.Sense ──> AI.Decide ──> AI.Act   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

```cpp
void register_game_systems(Runtime* rt) {
    Movement::init(rt);
    AI::init(rt);

    // AI sees updated positions after Movement resolves
    AI::Phase::Sense.add(flecs::DependsOn, Movement::Phase::Resolve);
}
```

> **See:** [examples/domains/game_init.cpp](examples/domains/game_init.cpp) for complete example

## Writing Systems

### System Function Signatures

Flecs `.each()` supports three callback signatures:

| Signature | Use When |
|-----------|----------|
| `void func(Components&...)` | No entity or delta_time needed |
| `void func(flecs::entity, Components&...)` | Need to add/remove tags or query entity |
| `void func(flecs::iter&, size_t, Components&...)` | Need `it.delta_time()` |

### Guidelines

| Rule | Example |
|------|---------|
| Check Gd:: validity | `if (!node.is_valid()) return;` |
| Use `.each()` with named functions | Clean, readable registration |
| Use `.with<Tag>()` / `.without<Tag>()` | Filter at query level, not runtime |
| Static functions | `static void my_system(...)` — private to file |

### Named Function (Preferred)

```cpp
// Simple — just components
static void health_regen(Health& hp) {
    hp.current = fminf(hp.current + 1.0f, hp.max);
}

// With entity — for tag manipulation
static void check_death(flecs::entity e, Health& hp) {
    if (hp.current <= 0) {
        e.add<Tag::Dead>();
    }
}

// With iter — for delta_time
static void apply_gravity(flecs::iter& it, size_t i, Velocity& vel) {
    vel.linear.y -= 9.8f * it.delta_time();
}
```

### Registration Pattern

```cpp
// Simple components-only
w.system<Health>("HealthRegen")
    .kind(physics)
    .without<Tag::Dead>()
    .each(health_regen);

// With entity access
w.system<Health>("CheckDeath")
    .kind(physics)
    .without<Tag::Dead>()
    .each(check_death);

// With delta_time (grounded entities excluded at query level)
w.system<Velocity>("ApplyGravity")
    .kind(physics)
    .without<Tag::Grounded>()
    .each(apply_gravity);
```

## Registration Patterns

### Filters

```cpp
// Only players
w.system<PlayerInputState>("CaptureInput")
    .kind(input)
    .with<Tag::Player>()
    .each(capture_input);

// Exclude dead entities
w.system<Health>("Regen")
    .kind(physics)
    .without<Tag::Dead>()
    .each(regen);
```

### Multiple Component Types

```cpp
w.system<const Velocity, Gd::CharacterBody3D>("ApplyVelocity")
    .kind(physics)
    .each(apply_velocity);
```

## Summary

| Concept | Description |
|---------|-------------|
| **Domain Module** | Self-contained namespace with `init()` entry point |
| **Sub-Phase** | Custom phase for fine-grained ordering within a domain |
| **DependsOn** | Explicit ordering between phases |
| **Static Systems** | Private to file — encapsulation |
| **`.each()` with named functions** | Preferred — clean, readable system registration |
