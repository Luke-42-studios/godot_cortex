# Coding Standards

> Data-Oriented C++ — Simple, predictable, cache-friendly

---

## Overview

Polaris follows **Data-Oriented Design** principles. Write simple, predictable C++ that prioritizes data layout and bulk processing over abstractions.

The goal: data layout matters, process in bulk, minimize cache misses.

---

## What to Use

| Use | For |
|-----|-----|
| POD structs | All components |
| Plain functions | All systems |
| `flecs::entity` | Entity handles |
| Godot types (Vector3, Transform3D, etc.) | Math in components (they're POD) |
| Direct Godot pointers | Gd:: components |
| Arenas | Temporary allocations |
| Namespaces | Organization (Polaris::, Tag::, Gd::) |
| `enum class` | State machines, flags |

---

## What to Avoid

| Avoid | Why | Instead |
|-------|-----|---------|
| Inheritance for game objects | Hidden behavior, cache unfriendly | Composition via ECS |
| Virtual functions in hot paths | Indirect calls, cache misses | Plain functions |
| `std::vector`, `std::string` in components | Hidden allocations, not POD | Fixed arrays, arena strings |
| RAII in components | Hidden behavior on copy/move | Explicit setup/teardown |
| Scattered malloc/free | Fragmentation, cache misses | Arena allocators |
| Getters/setters | Unnecessary indirection | Direct field access |
| `this->` | Noise | Just use field name |
| Multiple bools for state | Wastes space, unclear | `enum class` |

---

## Component Guidelines

Components are **POD structs** — plain old data with no hidden behavior.

### Layout Rules

1. **Largest fields first** — reduces padding
2. **Group related data** — better cache behavior
3. **Explicit padding** — document your intent
4. **No pointers to dynamic memory** — use entity IDs or arena allocations

### Good Components

```cpp
// GOOD: POD struct, tightly packed
struct Health {
    float current;    // 4 bytes
    float max;        // 4 bytes
};                    // 8 bytes total

// GOOD: Godot types are POD
struct Velocity {
    godot::Vector3 linear;    // 12 bytes
    godot::Vector3 angular;   // 12 bytes
};                            // 24 bytes total

// GOOD: State as enum, explicit padding
enum class AIState : uint8_t {
    Idle, Patrol, Chase, Attack
};

struct AI {
    flecs::entity target;     // 8 bytes (entity ID, not pointer)
    float timer;              // 4 bytes
    float aggro_range;        // 4 bytes
    AIState state;            // 1 byte
    uint8_t padding[3];       // 3 bytes (explicit)
};                            // 20 bytes total

// GOOD: Fixed-size array for bounded data
struct Inventory {
    flecs::entity items[8];   // 64 bytes
    uint8_t count;            // 1 byte
    uint8_t padding[7];       // 7 bytes
};                            // 72 bytes total
```

### Bad Components

```cpp
// BAD: Multiple bools waste space
struct AIBad {
    bool is_idle;      // 1 byte + 7 padding
    bool is_chasing;   // 1 byte + 7 padding
    void* target;      // 8 bytes (pointer, not ID)
};                     // 24 bytes with padding

// BAD: std::vector is not POD
struct InventoryBad {
    std::vector<Item> items;  // Hidden allocations!
};

// BAD: Pointer to external memory
struct MeshBad {
    Vertex* vertices;   // Who owns this? When freed?
    size_t count;
};
```

## Component Types: Config vs State

Components fall into two categories based on their purpose and lifecycle:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│   COMPONENT TYPES                                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   CONFIG COMPONENTS                        STATE COMPONENTS                 │
│   ─────────────────                        ────────────────                 │
│   Purpose: Settings from editor            Purpose: Runtime gameplay data   │
│   Source:  Copied from Godot Resource      Source:  Initialized in compose  │
│   Mutated: Rarely (live editing only)      Mutated: Every frame by systems  │
│   Naming:  {Feature}Config                 Naming:  {Feature}State          │
│                                                                             │
│   Examples:                                Examples:                        │
│   ├── CrouchConfig                         ├── CrouchState                  │
│   ├── BobConfig                            ├── BobState                     │
│   ├── LandingConfig                        ├── LandingState                 │
│   └── StrafeRollConfig                     └── StrafeRollState              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Config Components

Config components hold **parameters set in the editor**. They're copied from Godot Resources into ECS at compose time.

```cpp
// Config: read by systems, set from editor
struct CrouchConfig {
    float stand_height = 72.0f;
    float crouch_height = 36.0f;
    float transition_speed = 10.0f;
    TweenAnimation transition;  // Easing curve
};
```

### State Components

State components hold **data that changes during gameplay**. Systems read and write these every frame.

```cpp
// State: modified by systems each frame
struct CrouchState {
    float transition = 0.0f;    // 0 = standing, 1 = crouched
    bool wants_crouch = false;  // Input from player
};
```

### The Config Resource Pattern

Config data flows from **Godot Resource → Composition → ECS Component**:

```
┌──────────────────┐     compose()     ┌──────────────────┐
│  Godot Resource  │ ───────────────►  │  ECS Component   │
│  (player.tres)   │    copy fields    │  (CrouchConfig)  │
└──────────────────┘                   └──────────────────┘
       │                                        │
       │ Inspector edits                        │ Systems read
       ▼                                        ▼
  ┌──────────┐                           ┌──────────────┐
  │ Designer │                           │ crouch_system│
  └──────────┘                           └──────────────┘
```

### Creating a Config Resource

Use **X-Macros** with **POLARIS_ACCESSORS** and **POLARIS_BIND** macros to define config components. The pattern keeps structs as plain POD (ECS-friendly) and moves all unit conversions to systems.

**Step 1: Define X-Macro for property metadata**

```cpp
// X(field_name, cpp_type, GODOT_TYPE, "inspector/path", "hint", ...)
#define CROUCH_CONFIG_PROPS(X, ...) \
    X(stand_height,     float, FLOAT, "crouch/stand_height",     "", __VA_ARGS__) \
    X(crouch_height,    float, FLOAT, "crouch/crouch_height",    "", __VA_ARGS__) \
    X(transition_speed, float, FLOAT, "crouch/transition_speed", "", __VA_ARGS__)
```

**Step 2: Define plain POD structs (no macros in struct)**

```cpp
// Config: Inspector values - plain POD struct
struct CrouchConfig {
    float stand_height{};       // meters
    float crouch_height{};      // meters
    float transition_speed{};   // units/sec
};

// State: Runtime values - SEPARATE struct
struct CrouchState {
    float transition{};     // 0 = standing, 1 = crouched
    bool wants_crouch{};    // Input from player
};
```

**Why Plain POD?**
- ECS can easily read/serialize the struct
- Clear, readable field definitions
- No hidden macro expansion in data layout

**Step 3: Composition uses POLARIS_ACCESSORS**

```cpp
class Pawn : public Composition {
    GDCLASS(Pawn, Composition)

protected:
    static void _bind_methods();

    // Config member (serialized to .tres)
    CrouchConfig m_crouch;

public:
    // Generated accessors via Polaris macro (passthrough + sync)
    POLARIS_ACCESSORS(CrouchConfig, m_crouch, CROUCH_CONFIG_PROPS)

    void compose(flecs::entity e, Node* node) override;
    void decompose(flecs::entity e) override;
};
```

**Step 4: Use POLARIS_BIND in _bind_methods()**

```cpp
void Pawn::_bind_methods() {
    ADD_GROUP("Crouch", "crouch/");
    POLARIS_BIND(Pawn, CROUCH_CONFIG_PROPS)
}
```

**Step 5: Set config and state in compose()**

```cpp
void Pawn::compose(flecs::entity e, Node* node) {
    Composition::compose(e, node);

    // Config (from .tres) - no conversion, just copy
    e.set<CrouchConfig>(m_crouch);

    // State (fresh) - runtime values start at defaults
    e.set<CrouchState>({});
}
```

### Systems Do ALL Conversions

Unit conversions happen in systems, not in accessors or compose(). This keeps config structs simple and explicit.

```cpp
static void crouch_system(flecs::iter& it, size_t i,
                          const CrouchConfig& config, CrouchState& state,
                          Gd::CharacterBody3D& body) {
    if (!body.is_valid()) return;

    // CONVERSION HERE if needed (e.g., if storing HU in config)
    float target_height = state.wants_crouch
        ? config.crouch_height
        : config.stand_height;

    // Interpolate transition
    state.transition = Math::move_toward(state.transition,
        state.wants_crouch ? 1.0f : 0.0f,
        config.transition_speed * it.delta_time());

    // Apply height
    float current_height = Math::lerp(config.stand_height, config.crouch_height, state.transition);
    // ...
}
```

**Key points:**
- Define property metadata **once** in X-Macro
- Structs are **plain POD** (no macros in struct definition)
- Config and State are **separate structs**
- `POLARIS_ACCESSORS` generates get/set + `sync<T>()` call
- `POLARIS_BIND` generates ClassDB bindings
- Systems do **all conversions** (no pack() method needed)

### Other Component Types

| Type | Purpose | Example |
|------|---------|---------|
| **Tag** | Empty marker for filtering | `Tag::Player`, `Tag::Enemy` |
| **Ref** | Godot node reference | `Gd::Node3D`, `Gd::Camera3D` |
| **Accumulator** | Collects output from multiple systems | `CameraOffsets` (bob + roll + dip) |

### Summary

| Aspect | Config | State |
|--------|--------|-------|
| **Purpose** | Editor parameters | Gameplay data |
| **Source** | Godot Resource (.tres) | Initialized in compose() |
| **Lifetime** | Set once, rarely changes | Changes every frame |
| **Systems** | Read only | Read and write |
| **Naming** | `{Feature}Config` | `{Feature}State` |

## System Guidelines

Systems are **plain functions** that operate on component data.

### Function Signatures

Flecs `.each()` supports three callback signatures:

```cpp
// Simple — just components
static void health_regen(Health& hp) {
    hp.current = fminf(hp.current + 1.0f, hp.max);
}

// With entity — for tag manipulation
static void check_death(flecs::entity e, Health& hp) {
    if (hp.current <= 0) e.add<Tag::Dead>();
}

// With iter — for delta_time access
static void apply_gravity(flecs::iter& it, size_t i, Velocity& vel) {
    vel.linear.y -= 9.8f * it.delta_time();
}
```

### System Rules

1. **Check validity** — Gd:: components may have null pointers
2. **Use `.each()` with named functions** — clean, readable registration
3. **Use `.with<Tag>()` / `.without<Tag>()`** — filter at query level, not runtime
4. **Avoid allocations** — use phase arena for temp data
5. **No side effects outside ECS** — except through Gd:: components

### Good Systems

```cpp
// GOOD: Named function with reference params
static void apply_velocity(const Velocity& vel, Gd::CharacterBody3D& body) {
    if (!body.is_valid()) return;
    body.set_velocity(vel.linear);
    body.move_and_slide();
}

static void resolve_velocity(Velocity& vel, Gd::CharacterBody3D& body) {
    if (!body.is_valid()) return;
    vel.linear = body.get_velocity();
}

// GOOD: Uses arena for temp allocation (use .run() for shared scratch)
static void find_nearby_enemies(flecs::iter& it) {
    Arena* arena = &runtime()->phases[Phase_Physics].arena;

    // Temp array freed at phase end, shared across all entities
    flecs::entity* nearby = (flecs::entity*)arena_alloc(
        arena, 32 * sizeof(flecs::entity), alignof(flecs::entity)
    );

    while (it.next()) {
        auto ai = it.field<AI>(0);
        for (auto i : it) {
            // Use nearby array...
        }
    }
    // No free needed
}
```

### Bad Systems

```cpp
// BAD: Allocates every frame
static void find_nearby_bad(AI& ai) {
    std::vector<Entity> nearby;  // malloc every frame per entity!
    // ...
}

// BAD: Runtime tag check instead of query filter
static void process_bad(flecs::entity e, Health& hp) {
    if (e.has<Tag::Dead>()) return;  // Should use .without<Tag::Dead>()
    // ...
}
// BETTER: Use .without<Tag::Dead>() in system registration
```

## System Registration

Register systems to specific phases during initialization using `.each()` with named functions.

```cpp
static void apply_velocity(const Velocity& vel, Gd::CharacterBody3D& body) {
    if (!body.is_valid()) return;
    body.set_velocity(vel.linear);
    body.move_and_slide();
}

static void player_movement(const InputState& input, const MoveSpeed& speed,
                            Velocity& vel, Gd::Node3D& node) {
    if (!node.is_valid()) return;
    // Apply input to velocity
}

void register_movement_systems(Runtime* rt) {
    flecs::world& w = rt->world();
    flecs::entity physics = rt->get_phase(Phase_Physics).id;

    w.system<const Velocity, Gd::CharacterBody3D>("ApplyVelocity")
        .kind(physics)
        .each(apply_velocity);

    w.system<const InputState, const MoveSpeed, Velocity, Gd::Node3D>("PlayerMovement")
        .kind(physics)
        .with<Tag::Player>()
        .each(player_movement);
}
```

## Threading Rules

Polaris systems run on the **main thread** by default. This is critical for Godot API safety.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│   THREADING RULES                                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   MAIN THREAD ONLY:                                                         │
│   ├── All Gd:: component methods (set_position, move_and_slide, etc.)       │
│   ├── Godot singleton access (Input, PhysicsServer, etc.)                   │
│   ├── Node tree modifications (add_child, remove_child)                     │
│   └── Entity creation/destruction                                           │
│                                                                             │
│   SAFE FOR WORKER THREADS:                                                  │
│   ├── Pure math on data components (no Godot types)                         │
│   ├── Reading component data (if not being written)                         │
│   └── Arena allocations (if arena is thread-local)                          │
│                                                                             │
│   NEVER FROM WORKER THREADS:                                                │
│   ├── Calling Godot APIs                                                    │
│   ├── Accessing Gd:: component pointers                                     │
│   └── Modifying the flecs world structure                                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Safe Pattern: Main Thread Only (Default)

```cpp
// All systems run on main thread by default
static void apply_velocity(const Velocity& vel, Gd::CharacterBody3D& body) {
    if (!body.is_valid()) return;
    body.set_velocity(vel.linear);  // Safe: main thread
    body.move_and_slide();          // Safe: main thread
}
```

### Worker Thread Pattern (Advanced)

If you need parallel processing, isolate the Godot calls:

```cpp
// Phase 1: Parallel math (no Godot calls)
static void calculate_velocities(const Input& input, Velocity& vel) {
    // This could run on worker threads - pure math only
    vel.linear = calculate_from_input(input);  // Pure math
}

// Phase 2: Apply to Godot (main thread)
static void apply_to_godot(const Velocity& vel, Gd::CharacterBody3D& body) {
    // Must run on main thread
    if (!body.is_valid()) return;
    body.set_velocity(vel.linear);
}
```

### Cross-Phase Data Sharing

Data that needs to persist across phases must be in **components**, not arenas.

```cpp
// WRONG: Arena data doesn't persist
static void phase1_system_bad(SomeComponent& comp) {
    Arena* arena = &runtime()->phases[Phase_Physics].arena;
    float* results = arena_alloc(arena, ...);
    // results freed at phase end!
}

// RIGHT: Store in component
struct CalculationResult {
    float value;
};

static void phase1_system(CalculationResult& result) {
    result.value = calculate();  // Persists to next phase
}
```

## Component Sizes

For DOD, know your component sizes. Smaller = better cache behavior.

| Component | Size | Cache Lines | Notes |
|-----------|------|-------------|-------|
| `Health` | 8 bytes | 1/8 | Two floats |
| `MoveSpeed` | 4 bytes | 1/16 | Single float |
| `Velocity` | 24 bytes | 3/8 | Two Vector3s |
| `AI` | 20 bytes | ~1/3 | Entity + floats + enum + padding |
| `InputState` | 20 bytes | ~1/3 | Two Vector2s + bools + padding |
| `Gd::Node3D` | 8 bytes | 1/8 | Single pointer |
| `Gd::CharacterBody3D` | 8 bytes | 1/8 | Single pointer |
| `Tag::Player` | 0 bytes | 0 | Empty struct |

### Size Guidelines

| Size | Recommendation |
|------|----------------|
| < 64 bytes | Ideal — fits in one cache line |
| 64-128 bytes | OK for less frequent access |
| > 128 bytes | Consider splitting into multiple components |

### Measuring Size

```cpp
// Compile-time size check
static_assert(sizeof(Health) == 8, "Health should be 8 bytes");
static_assert(sizeof(Velocity) == 24, "Velocity should be 24 bytes");
static_assert(sizeof(AI) == 20, "AI should be 20 bytes");

// Runtime logging
Log::info("Health size: ", sizeof(Health));
Log::info("AI size: ", sizeof(AI));
```

## Naming Conventions

### Namespace Structure

```
┌─────────────────────────────────────────────────────────────────────────────┐
│   NAMESPACE HIERARCHY                                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Polaris::                    Engine code (Runtime, Composition, etc.)     │
│   │                                                                         │
│   ├── Gd::                     Godot node wrappers                          │
│   │   ├── Node                 Generic node reference                       │
│   │   ├── Node3D               3D transform helpers                         │
│   │   ├── Node2D               2D transform helpers                         │
│   │   └── CharacterBody3D      Physics body wrapper                         │
│   │                                                                         │
│   └── Tag::                    Zero-size markers                            │
│       ├── Player               Player-controlled entity                     │
│       ├── Enemy                AI-controlled enemy                          │
│       ├── Grounded             On floor flag                                │
│       └── Dead                 Death state                                  │
│                                                                             │
│   Game::                       Your game code                               │
│   │                                                                         │
│   ├── (flat)                   Data components (Health, Velocity, AI)       │
│   │                                                                         │
│   ├── Tag::                    Game-specific tags                           │
│   │   └── Interactable         Custom game tag                              │
│   │                                                                         │
│   └── Systems/Domains          Domain modules (Movement::, Combat::)        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Naming Rules

| Type | Namespace | Convention | Example |
|------|-----------|------------|---------|
| **Data Components** | Flat (Game::) | PascalCase | `Health`, `Velocity`, `AI` |
| **Gd:: Components** | `Polaris::Gd::` | Gd::NodeType | `Gd::Node3D`, `Gd::CharacterBody3D` |
| **Tags** | `Polaris::Tag::` or `Game::Tag::` | Tag::PascalCase | `Tag::Player`, `Tag::Dead` |
| **Systems** | Domain namespace | snake_case function | `Movement::player_movement` |
| **Domain Modules** | Game:: | PascalCase namespace | `Movement::`, `Combat::`, `AI::` |
| **Phases** | `Polaris::` | Phase_PascalCase | `Phase_Physics`, `Phase_Input` |

### Declaration Examples

```cpp
// Polaris engine provides Gd:: and Tag:: namespaces
namespace Polaris {
    namespace Gd {
        struct Node3D { ... };
        struct CharacterBody3D { ... };
    }
    namespace Tag {
        struct Player {};
        struct Enemy {};
    }
}

// Your game defines components at flat level
namespace Game {
    // Data components (flat, no sub-namespace)
    struct Health { float current, max; };
    struct Velocity { Vector3 linear, angular; };
    struct AI { ... };

    // Game-specific tags
    namespace Tag {
        struct Interactable {};
        struct QuestGiver {};
    }

    // Systems organized by domain
    namespace Movement {
        void init(Polaris::Runtime* rt);
    }
    namespace Combat {
        void init(Polaris::Runtime* rt);
    }
}
```

### Usage in Code

```cpp
using namespace Polaris;  // Access Gd::, Tag::, runtime(), etc.
using namespace Game;     // Access Health, Velocity, Movement::, etc.

// Use .with<Tag>() for filtering rather than runtime checks
static void player_health_update(Health& hp, Gd::Node3D& node) {
    if (!node.is_valid()) return;
    // Only called for entities with Tag::Player (filtered at registration)
}

// Registration
w.system<Health, Gd::Node3D>("PlayerHealthUpdate")
    .kind(physics)
    .with<Tag::Player>()  // Filter at query level
    .each(player_health_update);
```

## Composition Guidelines

Compositions have a standard method ordering convention for readability:

### Method Ordering

| Order | Section | Methods |
|-------|---------|---------|
| 1 | **Composition Lifecycle** | `compose()`, `decompose()` |
| 2 | **Godot Bindings** | `_bind_methods()`, getters/setters |

The main logic (`compose`/`decompose`) comes **first** because it's what matters most. Godot bindings are boilerplate and go **last**.

### Example Structure

```cpp
// =============================================================================
// Composition Lifecycle (main logic - comes first)
// =============================================================================

void PlayerPawn::compose(flecs::entity e, Node* node) {
    Pawn::compose(e, node);
    // Add player-specific components
    e.set<PlayerInputState>({});
    e.add<Tag::Player>();
}

void PlayerPawn::decompose(flecs::entity e) {
    // Unbind custom Gd:: components
    if (auto* c = e.try_get_mut<Gd::Camera3D>()) c->unbind();
    Pawn::decompose(e);
}

// =============================================================================
// Godot Bindings (boilerplate - comes last)
// =============================================================================

void PlayerPawn::_bind_methods() {
    ClassDB::bind_method(D_METHOD("get_sensitivity"), &PlayerPawn::get_sensitivity);
    ClassDB::bind_method(D_METHOD("set_sensitivity", "value"), &PlayerPawn::set_sensitivity);
    ADD_PROPERTY(PropertyInfo(Variant::FLOAT, "sensitivity"), "set_sensitivity", "get_sensitivity");
}
```

### Section Comments

Use section comments to clearly separate lifecycle from bindings:

```cpp
// =============================================================================
// Composition Lifecycle
// =============================================================================

// =============================================================================
// Godot Bindings
// =============================================================================
```

## File Organization

```
game/
├── components/
│   ├── Data.h          # All data components in one header
│   ├── Tags.h          # All tag components
│   └── Gd.h            # Game-specific Gd:: components
│
├── systems/
│   ├── input.cpp       # Phase_Input systems
│   ├── movement.cpp    # Phase_Physics movement
│   ├── combat.cpp      # Phase_Physics combat
│   ├── ai.cpp          # Phase_Physics AI
│   └── animation.cpp   # Phase_Process animation
│
└── compositions/
    ├── Pawn.h/.cpp
    └── PlayerPawn.h/.cpp
```

### Header Guidelines

- **Components**: All in headers (they're just structs)
- **Systems**: Declare registration function in header, implement in cpp
- **One header per concern**: Don't scatter related components

```cpp
// components/Data.h
#pragma once

struct Health {
    float current;
    float max;
};

struct Velocity {
    godot::Vector3 linear;
    godot::Vector3 angular;
};

struct MoveSpeed {
    float value;
};

// ... all data components
```

```cpp
// systems/movement.h
#pragma once

namespace Polaris {
class Runtime;  // Godot Object
}

namespace Game::Systems {
void register_movement_systems(Polaris::Runtime* rt);
}
```

## Summary

| Principle | Practice |
|-----------|----------|
| **Data-Oriented** | POD structs, bulk processing, cache-friendly layout |
| **Simple C++** | Plain functions, no inheritance, explicit memory |
| **Predictable** | No hidden allocations, no hidden behavior |
| **Explicit** | Visible data layout, visible control flow |

Write code that you can reason about by reading it. No magic, no surprises.
