# Composition

> **C** in CELS — Define entity archetypes and link C++ logic to Godot views

---

## Overview

A **Composition** is a Godot Resource that defines what an entity is made of. It bridges C++ ECS logic with Godot's visual scene tree (the "view"). When a node has a Composition in its metadata, Polaris creates an entity and calls `compose()` to set up components.

```
Node + Metadata["composition"] = Entity
```

## Designer Units

Compositions store values in **designer-friendly units** that are easy to understand and edit. Systems use **Godot units** (meters, radians) internally. **Conversion happens in systems** when reading config values — this keeps components as pure data and makes conversions explicit.

**Location:** `src/polaris/src/core/Units.h`

### Domain Rules

| Domain | Designer Unit | Godot Unit | Why Designer Unit |
|--------|---------------|------------|-------------------|
| **Speed** | HU/s | m/s | Source docs use HU, "320 = walk" is universal |
| **Distance (large)** | HU | meters | Player height = 72 HU, matches Source games |
| **Distance (small)** | cm | meters | "2.5 cm bob" is tangible, 0.025m is abstract |
| **Rotation** | degrees | radians | Everyone knows 90° = right angle |
| **Sensitivity** | % (0-100) | raw mult | "20% sensitivity" is intuitive |
| **Multiplier** | % (0-100) | 0.0-1.0 | "50% speed" is clear |
| **Acceleration** | HU/s² | m/s² | 800 gravity is iconic from Source |
| **Time** | seconds | seconds | Already intuitive (no conversion) |

### Property Naming Convention

Use suffixes to make units explicit in the inspector:

```cpp
// Config struct - designer units with suffix
struct BobConfig {
    float vertical_cm{};      // Centimeters
    float horizontal_cm{};    // Centimeters
    float frequency{};        // Hz (no suffix needed)
};

struct StrafeRollConfig {
    float angle_deg{};        // Degrees
    float roll_speed{};       // Speed factor
};
```

### Conversion in Systems (Recommended)

Systems convert designer units to Godot units when reading config:

```cpp
#include "core/Units.h"

static void head_bob_system(flecs::iter& it, size_t i,
                            const BobConfig& config, BobState& state, ...) {
    using namespace Units;

    // CONVERSION HERE: cm → meters
    float vertical_amp = Distance::cm_to_godot(config.vertical_cm);   // 2.5 → 0.025
    float horizontal_amp = Distance::cm_to_godot(config.horizontal_cm);

    // Use converted values for calculations
    // ...
}

static void strafe_roll_system(flecs::iter& it, size_t i,
                               const StrafeRollConfig& config, ...) {
    using namespace Units;

    // CONVERSION HERE: degrees → radians
    float roll_angle = Rotation::to_godot(config.angle_deg);  // 0.65 → 0.0113

    // CONVERSION HERE: int → enum
    EasingCurve curve;
    curve.trans = static_cast<Tween::TransitionType>(config.roll_trans);
    curve.ease = static_cast<Tween::EaseType>(config.roll_ease);
}
```

**Why convert in systems?**
- Components stay as pure data (no derived fields)
- Conversions are explicit and visible where they're used
- Easier to debug (inspect raw config values)
- No `pack()` method needed

### Inspector Property Hints

Use ranges that make sense for designer units:

```cpp
// Good: Designer-friendly ranges

    PROPERTY_HINT_RANGE, "0,500,1"), ...);           // Whole HU, easy slider
```

## Config vs State Components

Components fall into two categories: **Config** (tunable parameters) and **State** (runtime data). Understanding the difference is essential for proper composition design.

### Config Components

**Purpose:** Store tunable parameters that define behavior. Set once in `compose()`, optionally updated via inspector at runtime.

**Characteristics:**
- Values come from composition properties (inspector-editable)
- Read by systems, rarely modified during gameplay
- Can be live-edited if setters update the ECS component

```cpp
// Config: Defines HOW the bob effect works
struct BobConfig {
    float frequency = 2.0f;      // Bob cycles per second
    float vertical_amp = 0.025f; // How much vertical movement
    float horizontal_amp = 0.01f;// How much horizontal sway
    bool enabled = true;         // Can be toggled
};
```

### State Components

**Purpose:** Store runtime data that changes every frame. Initialized fresh in `compose()`, modified by systems during gameplay.

**Characteristics:**
- Not exposed to inspector (internal runtime data)
- Modified by systems each frame
- Reset to defaults in `compose()`

```cpp
// State: Tracks WHERE we are in the bob cycle
struct BobState {
    float phase = 0.0f;          // Current position in cycle (0 to 2π)
    float current_speed = 0.0f;  // Smoothed player speed
};
```

### The Config/State Pattern

Always pair a Config component with a State component:

```cpp
void PlayerPawn::compose(flecs::entity e, Node* node) {
    // Config: Copy from composition (inspector values)
    e.set<BobConfig>(m_bob);

    // State: Fresh instance (default-initialized)
    e.set<BobState>({});

    // Config: Copy from composition
    e.set<StrafeRollConfig>(m_strafe_roll);

    // State: Fresh instance
    e.set<StrafeRollState>({});
}
```

### Why Separate Them?

| Aspect | Config | State |
|--------|--------|-------|
| Source | Inspector / .tres file | Computed at runtime |
| Lifetime | Persistent | Transient |
| Editor exposure | Yes (properties) | No (internal) |
| Modified by | Setters (live edit) | Systems (every frame) |
| Reset on respawn | Usually kept | Always reset |

### Component Naming Convention

| Component Type | Naming | Example |
|----------------|--------|---------|
| Config | `XxxConfig` | `BobConfig`, `CrouchConfig` |
| State | `XxxState` | `BobState`, `CrouchState` |
| Combined (simple) | Just the name | `Health`, `Velocity` |

Simple components that mix config and state (like `Health` with `current` and `max`) are acceptable for straightforward cases. Use the Config/State split when the config has many tunable parameters.

## Runtime Property Updates (Live Editing)

Compositions support **live editing**: changing inspector values while the game runs updates behavior immediately. Use the **sync pattern** for this.

### The sync<T>() Pattern

Setters call `sync<T>()` which pushes the config to ECS:

```cpp
class PlayerPawn : public Pawn {
protected:
    BobConfig m_bob;  // Config member (serialized to .tres)

public:
    // Setters update member and sync to ECS
    void set_frequency(float v) { m_bob.frequency = v; sync<BobConfig>(m_bob); }
    float get_frequency() const { return m_bob.frequency; }

    void compose(flecs::entity e, Node* node) override {
        Pawn::compose(e, node);

        // Config: copy from .tres (no conversion)
        e.set<BobConfig>(m_bob);

        // State: fresh instance
        e.set<BobState>({});
    }
};
```

**Key points:**
- `sync<T>()` is provided by `Composition` base class
- No `pack()` method needed — components store raw editor values
- Systems do conversions when reading config

### When to Use Live Editing

| Use Case | Live Edit? | Notes |
|----------|------------|-------|
| Tuning feel (bob, roll) | Yes | Instant feedback while playing |
| Movement params | Yes | Test different speeds without restart |
| Health/damage values | Optional | Less critical for feel |
| Structural changes | No | Require re-compose (e.g., adding components) |

### POLARIS_ACCESSORS Pattern (Recommended)

For reduced boilerplate, use **POLARIS_ACCESSORS** to generate setters and **POLARIS_BIND** for ClassDB bindings:

```cpp
#include "polaris/src/core/PropertyMacros.h"

// X-macro defines properties once (C=Component, M=member)
#define BOB_PROPS(X, C, M) \
    X(frequency,   float, FLOAT, "bob/frequency", "", C, M) \
    X(vertical_cm, float, FLOAT, "bob/vertical",  "", C, M)

class PlayerPawn : public Pawn {
protected:
    BobConfig m_bob;

public:
    // Generates: set_frequency(), get_frequency(), set_vertical_cm(), etc.
    POLARIS_ACCESSORS(BobConfig, m_bob, BOB_PROPS)
};

// In _bind_methods()
void PlayerPawn::_bind_methods() {
    ADD_GROUP("Head Bob", "bob/");
    POLARIS_BIND(PlayerPawn, BOB_PROPS)
}
```

See **[Coding Standards](5.%20Coding%20Standards.md#creating-a-config-resource)** for the full pattern.

## POLARIS_ACCESSORS Pattern (Recommended)

The recommended approach uses **plain POD structs** as member variables with **POLARIS_ACCESSORS** to generate accessors and **POLARIS_BIND** for ClassDB bindings. This enables both .tres serialization AND live runtime editing with minimal boilerplate.

### Architecture

```
┌─────────────────────────────────────────────────────────────────────────────┐
│   POLARIS_ACCESSORS PATTERN                                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌─────────────────────┐         ┌─────────────────────┐                   │
│   │  Config Struct      │ sync<T> │  Entity Component   │                   │
│   │  (m_config)         │ ──────> │  (ECS)              │                   │
│   │                     │         │                     │                   │
│   │  Plain POD fields   │         │  Plain POD fields   │                   │
│   │  (no macros)        │         │  (same data)        │                   │
│   └─────────────────────┘         └─────────────────────┘                   │
│            ▲                               │                                │
│            │ setters call sync<T>()        │ systems read                   │
│   ┌────────┴────────────────────┐   ┌──────▼──────────────────┐             │
│   │  Inspector Properties       │   │  Systems convert inline │             │
│   │  (POLARIS_BIND from X-Macro)│   │  (Units::to_godot)      │             │
│   └─────────────────────────────┘   └─────────────────────────┘             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### How It Works

1. **Config struct** is plain POD (no macros in struct definition)
2. **State struct** is separate (runtime data, not serialized)
3. **X-Macro** defines property metadata for accessors and bindings
4. **POLARIS_ACCESSORS** generates get/set + `sync<T>()` call
5. **POLARIS_BIND** generates ClassDB bindings
6. **Systems** do all unit conversions when reading config

### Full Pattern

See **[Coding Standards - Creating a Config Resource](5.%20Coding%20Standards.md#creating-a-config-resource)** for the complete pattern with examples.

### Benefits

| Benefit | How |
|---------|-----|
| Plain POD structs | ECS-friendly, no macros in struct definition |
| Define metadata once | X-Macro generates only accessors and bindings |
| .tres serialization | Member struct serialized via property bindings |
| Live editing | Setters call `sync<T>()` → updates ECS immediately |
| No derived fields | Systems do conversions inline (simpler, more explicit) |
| Config/State separation | Clear ownership: Config read-only, State mutable |

## Implementing a Composition

### Class Definition

```cpp
class PlayerPawn : public Composition {
    GDCLASS(PlayerPawn, Composition)

    float m_max_health = 100.0f;

public:
    void compose(flecs::entity e, Node* root) override;
    void decompose(flecs::entity e) override;

protected:
    static void _bind_methods();
};
```

### compose() Pattern

| Step | API |
|------|-----|
| Call parent | `Composition::compose(e, root)` — sets `Gd::Node` + `Gd::Node3D` |
| Add data | `e.set<Health>({ .current = m_max_health, .max = m_max_health })` |
| Add tags | `e.add<Tag::Player>()` |

### decompose() Pattern

| Step | API |
|------|-----|
| Unbind custom | `if (auto* p = e.try_get_mut<T>()) p->unbind();` |
| Call parent | `Composition::decompose(e)` — unbinds `Gd::Node` + `Gd::Node3D` |

### Property Binding

| Binding | Purpose |
|---------|---------|
| `ClassDB::bind_method(D_METHOD("get_x"), &C::get_x)` | Getter |
| `ClassDB::bind_method(D_METHOD("set_x", "v"), &C::set_x)` | Setter |
| `ADD_PROPERTY(PropertyInfo(...), "set_x", "get_x")` | Inspector |

## Gd:: Components

**Location:** `src/polaris/src/components/Gd.h`

### Framework Components

| Component | Description | Auto-set |
|-----------|-------------|----------|
| `Gd::Node` | Generic node reference | Yes (always) |
| `Gd::Node3D` | 3D node with transform helpers | Yes (for 3D nodes) |
| `Gd::Node2D` | 2D node with transform helpers | No (set manually) |

### Common API Pattern

All Gd:: components implement:

| Method | Purpose |
|--------|---------|
| `static T create(Node*)` | Factory method |
| `is_valid()` | Check pointer before use |
| `unbind()` | Set pointer to nullptr (call in decompose) |

### Gd::Node3D Transform API

| Method | Return |
|--------|--------|
| `get_position()` / `set_position(Vector3)` | Global position |
| `get_rotation()` / `set_rotation(Quaternion)` | Rotation |
| `get_basis()` | Global basis matrix |
| `get_forward()` / `get_right()` / `get_up()` | Direction vectors |

### Gd::Node2D Transform API

| Method | Return |
|--------|--------|
| `get_position()` / `set_position(Vector2)` | Global position |
| `get_rotation()` / `set_rotation(float)` | Rotation in radians |

## Summary

1. Attach `Composition` resource to node via metadata
2. CompositionFactory creates entity, calls `compose()`
3. Base class auto-sets `Gd::Node` (always) + `Gd::Node3D` (for 3D nodes)
4. Add data components and tags in `compose()`
5. Systems query components to implement game logic
